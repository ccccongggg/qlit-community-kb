# 内容与运营维护规范

现行版本：2026-10-24。本文取代工作区早期的手写活动 HTML、重复维护成员详情页与手动资源版本号流程。

## 投稿接收与审核

1. 用户在 /participate/ 填写并生成草稿，再在 GitHub 检查、确认提交。没有 GitHub 账号时下载或复制草稿，交给已经认识的组织者。
2. 维护者在仓库 Issues 查看投稿，确认事实、来源、署名和素材授权。不要要求投稿人在公开 Issue 填写私人联系方式。
3. 确认可收录后，在 CMS 创建文章或更新数据。完成发布后在原 Issue 回复站内地址，再关闭已处理 Issue。提交成功不等同于审核或发布成功。
4. 每周查看未处理投稿、正在解决的问题与临近活动；每次活动后整理资料。这里是维护建议，不会自动创建定时任务。

## 文章与问题

source/_posts/*.md 为唯一内容源。必填标题、日期、分类、署名、内容状态；正式文章还需一句话摘要。

- content_status: published：可作为正式内容展示。
- content_status: example：保留旧示例，前台会显示提示，不进入首页精选。
- content_type：教程 / 经验 / 项目复盘 / 资源清单。
- tags：专业方向与文化标签。知学、知道、知善、知美不承担主分类职责。
- featured: true：正式知识可进入首页精选。
- updated：实质修改后更新，避免仅由文件复制时间决定。
- 问题分类填写“问题库”；problem_status 记录待讨论 / 招募中 / 处理中 / 已解决 / 暂缓，owner、progress、result_url、source_url 记录负责人、进展、成果和原讨论。

知识与问题列表由 {% hub knowledge %} / {% hub problems %} 标签生成。不要删除页面中的标签。页面内容缓存与脚本有关，修改生成脚本后全量 clean/build。

## 活动

唯一数据源：source/_data/activities.yml。CMS 中的活动安排和历史活动使用相同字段，详情页自动生成。

- slug 为稳定网址，不要在活动结束后修改。
- start、end、deadline 使用带 +08:00 的 ISO 时间。星期自动生成。
- status：即将开放 / 报名中 / 报名截止 / 已结束 / 已取消。
- 只有有效报名链接才能设为报名中；没有报名渠道时显示即将开放与咨询入口。
- 页面载入时会根据截止和结束时间更新状态；列表会把结束或取消的活动移到往期区域。
- 回顾写 recap，材料写 resources。活动照片和视频可通过有权公开的资料链接分享。

现有启动会源自 10 月 23 日策划案，容量与许可尚未确认，前台已标注。旧活动数据原样保存在 docs/archive/activities-before-2026-10-24.yml，核实后才能重新发布。

## 成员

source/_data/people.yml 单一数据源。published: false 不显示在列表，原链接保留为资料确认中页面；设为 true 前由本人确认公开信息。

只展示擅长领域名称，不用缺少依据的技能百分比。公开联系链接为 contact_url，帮助主题为 help，项目可填写 url。不填联系链接时提供参与入口，不伪造二维码。

## 预览、检查与发布

CMS 保存到 GitHub main，会生成提交。当前未配置站点实时 CMS 预览；不要把编辑面板当成实际排版预览。

本地先 npm run clean、npm run build、npm run check，再 npm run preview 看实际页面。GitHub 的 Build and validate 工作流也会构建、检查并保存静态预览产物，可下载后在本地静态服务打开。

npm run check 检查站内链接、资源路径、活动时间、重复标识和 CMS 数据文件。它不证明外链可访问、内容事实准确、后台登录成功或云端已上线。

正常发布仍按选定托管链路执行。发布后检查首页、搜索、参与入口、活动详情和移动导航，再核对一个新修改的内容。换域名时同步根配置 url 与 CMS site_url / display_url。

## 使用反馈

通过参与入口选择纠错，收集失败路径、找不到的内容与改进建议。先以公开反馈与实际投稿为依据，不增加未经说明的行为追踪。
